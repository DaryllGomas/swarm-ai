# Data policy

This is the developer version of [`/privacy`](https://swarm.bigpicsolutions.com/privacy). It says the same things in more detail, with the tables, columns and
functions that make them true. If the page and this file disagree, or either disagrees with the code, that is a bug: fix the one that is wrong and the test that
should have caught it. [ARCHITECTURE.md](ARCHITECTURE.md) ("Privacy and trust") explains how the pieces fit; [RUNBOOK.md](RUNBOOK.md) says what the maintainer checks and does.

Swarm is for people who value anonymity and decentralization, including protection against state actors and against punishment for what they choose to support.
The line is: **learn about the work, never about the people.** Defaults protect people who never read the screen. Never overclaim: wherever Swarm cannot protect
someone, the page says so in plain words (see "What Swarm cannot protect against").

## The rules for changing this code

1. **Classify every new piece of data into a tier** (below) before you store it, and add it to the table in this file and on `/privacy`. If it is about a person, ask whether Swarm needs it at all.
2. **Never store a name, an email address or a raw IP address.** Not in a column, an event, a log line, a test fixture or a response. Network addresses exist only as `HMAC(day key, network)` and only for about two days (the key for up to nearly three).
3. **Public aggregates that count people go through `kCount`** (`hub/src/privacy.js`); counts of voters and ballots go through the stricter `coarseCount` (see "The weekly vote, noise and k-anonymity"). A group below 5 shows as `fewer than 5`. Counts of work (units, tasks) are exact, **but only if they do not come from people's own choices (rule 10)**. A new endpoint that counts contributors, voters or any group of people needs a test next to `privacy-choices.test.js` that shows it.
4. **Public pages name a contributor only through `creditedAs` / `publicHandle`**, computed when the page is read, so a later change of credit applies to past records.
5. **Events carry no personal detail.** `events.detail` is for counts, kinds and ids of work. Never put a handle, an account id (even shortened), a network hash or the matched text of a personal detail in it. `actor` holds a role (`system`, `voter`, the reviewer's name) or, for claim and submission events, the contributor's handle, which account deletion, handle removal and `weekly_purge` scrub.
6. **`/ops` and `/api/admin` never return** an individual voter's ballot, a voter-to-contributor link, a network hash, or **how any task was routed** (public allocation, ballot or self-pick): no origin figure of any kind, live or weekly, and no contributor, handle, actor or origin on claim, link and steering events or on active claims. `operator-minimisation.test.js` scans every response, and `review6.test.js` builds worlds that differ only in the origin and requires every public and operator response to be identical; add new endpoints to both. **Direct database access is outside this boundary** (see "What the operator can and cannot see").
7. **Nothing may treat a caller differently by who they are**, beyond the network caps: no country, ASN, threat score, user agent or proxy-header checks. `trust.test.js` scans the source for them.
8. **Never edit a shipped migration.** Anything that needs the append-only tables (`events`, `ballot_versions`) to change is done through the narrow exceptions migration 0010 added (scrub to NULL; re-label to a random `gone:` id), nothing wider.
9. **The date on `/transparency` and the `Expires` of `security.txt` are constants in `hub/src/trust.js`.** They are renewed by a human on a schedule (RUNBOOK). Never make them dynamic: a statement that re-dates itself says nothing.
10. **Clever suppression loses to subtraction and polling, so remove a number rather than protect it.** Nothing public or operator-facing may separate personal steering (a ballot, a self-pick) from public routing: not a live figure, not a status change, not a refusal message, not an event, not a count. The live public figures are only: project-level OPEN task counts, the published weekly allocation and accepted results (receipts). The one routing figure is published weekly, for the closed week only: units claimed with **every route added together**, set beside the allocation in force (`/api/analytics`); it is coarser by design because it cannot isolate personal steering. Before adding any public number, ask what it can be subtracted from, and what two reads of it, or one read next to another endpoint, give away. `review6.test.js` has the pattern: build worlds that differ only in the secret and show every public and operator response is identical (and show the comparison can fail).
11. **Wording must not outrun the code.** `/privacy` says what is true, with its limits (see "Threat boundary"). Words such as "never", "nobody" and "cannot be picked out" are not used unless the design earns them.

## Three tiers

| Tier | What | How long |
|---|---|---|
| **Public record** | Aggregates and results: accepted work and receipts, weekly totals per project, weekly vote snapshots | Forever |
| **Running the system** | Individual detail that Swarm needs in order to work | Only as long as needed (table below) |
| **Never collected** | Names, email addresses, raw IP addresses, payment details, AI provider credentials | Not applicable |

## Network codes (forward secrecy)

- A network is the caller's IPv4 address, or an IPv6 address's first 64 bits (`networkOf` in `lib.js`). Its code for a day is `HMAC-SHA256(key of that UTC day, network)`, as lowercase hex (`ipHashFor`).
- The day's key is 32 random bytes in `network_keys(day, key)`, created on first use: `INSERT OR IGNORE`, then `SELECT`, so concurrent first uses all end up with one key (tested). A non-extractable `CryptoKey` is cached for five minutes in the isolate, and the cache is flushed when keys are deleted.
- Used for: the rate limiter key; the pairing cap (5 per network per day, `contributors.pair_ip`); the account cap (3 per day, `accounts.network`); the active-claim cap (4, `claims.network`); the link-attempt budget (`link_attempts.who`). Caps look at today's and yesterday's code, so midnight is no loophole. They also look at the same two in the pre-0010 format (`legacyIpHashFor`, `sha256(HASH_SALT|ip|day|network)`) until those rows are gone; the RUNBOOK says when to delete that.
- `forgetNetworks` (first in the hourly job) deletes keys whose whole UTC day is older than the cutoff (`day < utcDay(now - 2 days)`: today, yesterday and the day before survive, so **a key lives up to nearly three days**), and in the same batch sets `claims.network`, `contributors.pair_ip` and `accounts.network` to NULL where the **row** is older than two days, and deletes `link_attempts` older than two days. The job runs hourly, so each step can lag by up to an hour. A row's code is therefore erased before or when its key goes, never after.
- Effect, stated with its limits: **while a key exists, anyone who can read the database can compute the code of a candidate address and match it to the rows made that day** (`account` and `contributor` rows included, with no explicit voter-to-contributor link needed), and can relate rows from the same network. After a key is deleted from the live database nobody can reverse a code to a network or tell that two old rows came from the same one. That does not reach a copy of the key taken earlier (an export, D1 Time Travel, memory), which Swarm cannot find or destroy. `HASH_SALT` plays no part in network codes any more; it still salts contributor keys, sessions and link codes.

## The three choices

Stored on `accounts`; chosen at voter sign-up (`privacy` object on `POST /api/account/register/verify`) and edited on `/me` (`POST /api/me/privacy`). Each value has one sentence of explanation (`CHOICE_TEXT` in `privacy.js`; `common.js` shows the same sentences; a test keeps them equal) and a link to `/privacy`.

| Choice | Values | Default | What it does |
|---|---|---|---|
| `credit` | `anonymous`, `handle` | `anonymous` | Mirrored onto the contributors the account owns or is linked to (`mirrorCreditStmt`, on change, on `link_account`, on OAuth sign-in with a passkey). Contributors with no account are `anonymous` and use `set_credit`. Receipts say `a contributor` unless `credit = 'handle'`; computed at read time, so switching back hides the handle on past receipts |
| `history` | `private`, `weekly_purge` | `private` | `private`: own detail visible only to the owner on `/me`. `weekly_purge`: see "Retention" |
| `research` | `aggregate`, `share_pseudonymous` | `aggregate` | `share_pseudonymous` gives the account a random `research_id` (`r-` and 16 random characters, unrelated to the account id). ## Receipts and public stats

- `GET /api/receipts`: `credited_as` (`a contributor` / the handle / `removed contributor`), `handle` (null unless handle credit), `reviewed_at` as `YYYY-MM-DD` (UTC), no `self_reported`, no `model`, no `tokens_est`. For a pull request, `github.pr_author` is null unless handle credit; the pull-request link is always there. **GitHub itself shows the author**, which Swarm cannot change. A change of credit applies to receipts read from then on; it cannot recall a response or archive made earlier, and anonymous credit does not sever a PR, a source link or a publication from its author.
- Model and token figures are kept for the contributor's own `/me` and `my_week`, and for the reviewer (`/api/admin/pending`, the console). They are not in any public response, and not in the publication export (`/api/admin/submission`, `scripts/publish_townhall.py`).
- **Live: `GET /api/stats` and the `list_projects` tool** carry, per project: the allocation, `accepted_units` (this week and all time) and `open_tasks` (ready **or being worked**: a claim does not change it). **No routed or claimed units of any kind, no routed share, no gap reason built from them**, no claimed or released counts, no active claims, no pending-review counts, no contributor counts. `next_task` explains its pick with the published target only, not a routed share. Public task views (`/api/tasks`, `list_tasks`, `get_task`) show a claimed task as `ready` and list nothing as `claimed`.
- **Weekly: `GET /api/analytics`**, written once after a week closes: per project `claimed_units` (every route added together), its share of the week's total, the allocation in force, accepted units, task counts, contributors as a range, review times. This is the only place "did the scheduler follow the vote" is answered, and it is **coarser by design**: it cannot separate public routing from personal steering. There is no personal-direction figure.
- The k rule (`K_MIN = 5`) applies to counts of people. Zero is shown as 0. Units and task counts are exact only where rule 10 allows.

## The weekly vote, noise and k-anonymity

With one voter, a published split IS that voter's ballot, and two published splits can be differenced to recover a lone new ballot (Codex review 5, finding 1: the old daily projection did exactly this across a bucket boundary). So the vote is released once a week, with noise, and nothing else moves in between.

- **Snapshot.** `publishSnapshot` (`hub/src/voting.js`) runs once per ISO week. It reads the exact point totals of the eligible ballots, **adds Laplace noise to each project's total, clamps at zero and renormalises to 10000 basis points by the largest remainder method** (`noisedAllocation` in `hub/src/dp.js`), writes the noised split as the allocation and **discards the exact tally**. With fewer than 5 eligible ballots (no noise is drawn), or if every noised total is zero or less (noise was drawn and left nothing usable), the week is recorded with `source = 'fallback'`, `voter_count = 0` and the carried-forward previous split, marked provisional. **The two cases are stored and reported the same way**, as "no new result", because a noisy failure is not an exact fact about the electorate: the API reason is generic (usually too few ballots; rarely, unusable noise) and the count reads `not published`. The idealised chance of the second case with two projects and five 100-point ballots is about 0.17% (`exp(-5)/4`).
- **The noised split is THE official allocation.** The public pages, `/api/vote/current`, `/api/stats` and the scheduler's targets all use the same noised numbers, so no downstream figure (a routed-units chart, a receipt count) can reveal the exact tally.
- **Noise design, and what it is not.** One ballot is exactly 100 points, so adding or removing one ballot changes the vector of per-project totals by 100 points in total (L1 sensitivity 100; also at most 100 for any one project). Laplace noise of scale `100 / epsilon` per project, with epsilon = 1 (scale 100 points), is added to every active project's total, so one ballot cannot be read back from the split. Replacing a ballot can move the totals by 200. The noise comes from `crypto.getRandomValues`: 52 random bits n, mapped to `(n + 0.5) / 2^52`, which is exactly representable and always strictly between 0 and 1 (never 0, never 1), then the inverse Laplace transform; the sampler refuses any other value and a non-finite weight, so nothing infinite or NaN is stored. The generator is injectable in tests and nowhere else. Post-processing (clamping, renormalising, rounding) costs no privacy. **This is not a formal differential-privacy guarantee for the release as a whole, and Swarm does not claim one.** Around the noised split sit rules that depend on the ballots without any noise: a week needs 5 eligible ballots to publish a result at all (four ballots cannot, five can), the voter count is shown as a coarse bucket (nine ballots always show `5-9`, ten always `10-24`), and an unusable result falls back. Those outputs have disjoint support on neighbouring datasets, so no finite epsilon covers the release. What the noise does give is a practical protection for the split itself: with a fixed set of eligible ballots, differencing two releases does not recover a lone ballot (`dp.test.js` shows it fails with noise and succeeds without).
- **Nothing exact is stored.** The tally is computed, noised and dropped inside one function call; it is not in `vote_snapshots`, `allocation`, `meta`, a cache or a log. `vote_snapshots.voter_count` holds the lower edge of the coarse bucket (5, 10, 25, 50, 100, 150, ...), never the count. The snapshot is written once, so a second call cannot draw fresh noise to average the first away (`dp.test.js` checks this with racing publishers).
- **Repeated releases, stated plainly.** Each weekly release uses noise at epsilon 1. By the simplest accounting (basic composition) 52 weekly releases about the same unchanged ballot add up to epsilon 52 in the worst case. No tighter figure is claimed: an earlier "about 25 by advanced composition" estimate was wrong and is removed. There is no "epsilon budget" promise. An observer who sees the whole year can average much of the noise away for a stable electorate, so the noise protects a one-time change in one release well and a voter who is the same, in the same small group, for a year poorly. Raising protection means a smaller epsilon, a larger electorate, or releasing less often, and is a decision for the maintainer.
- **No projection.** `GET /api/vote/next` is gone (404). The vote page says the split is published each Monday. Daily projection caches (`meta` `projection:<day>`) were deleted by migration 0012.
- **Counts of voters and ballots** (`coarseCount`): a week with no published result shows no count (`not published`); below 5 (and zero too) `coarseCount` returns `fewer than 5`, because `0` next to `fewer than 5` would show that someone voted. From 5 they are published only as buckets (`5-9`, `10-24`, `25-49`, `50-99`, then steps of 50), whose lower edges are at least 5 apart, and the database keeps only the bucket. `GET /api/vote/audit` has weekly `snapshot_history` and the noise description, and **no** per-day counts and no live eligible-voter count (a number that moves during the week is a signal anyone can poll).
- **Residual risk, stated plainly.** (1) Someone who controls or knows 4 of 5 voters learns about the fifth; noise blurs a figure, it cannot hide what the observer already knows about the other four. (2) The noise protects one ballot per release, not a year of them (above). (3) The old tally existed in the database before migration 0012 and in any copy taken then. (4) Ballots themselves (`ballot_versions`) remain exact and private; anyone who can read the database can read them. (5) Whether a result was published, and the bucket of the count, are not noised (above). (6) A split published before the noise was added is exact (`noised = 0`): an earlier public exact result cannot be made private by adding noise later. Production is expected to have none; `deploy.sh` prints the number of snapshots built from ballots before it migrates.
- **The voter's own view.** `GET /api/ballot`, `GET /api/me` and the `/vote` and `/me` pages show the signed-in voter their own ballot. Nothing else does.

## How routing is kept out of public view

Work that a voter's own ballot steered (`ballot_directed`) or that an agent picked itself (`self_picked`) comes from people's own choices. The rule (Codex review 6, finding B) is the strongest simple one: **nobody sees which work was routed publicly and which was steered or self-picked, live or weekly, not even the operator console.**

- **Where the origin lives.** `claims.routing_origin` (and `routed`) stay in D1 for the scheduler only: the public-routed deficit against the allocation, and a ballot's own directed units against that ballot. **The database holds it next to the contributor, and the operator, with direct database access, could read it** (see "What the operator can and cannot see").
- **What was removed.** No live routed or claimed units and no routed share (`/api/stats`, `list_projects`); no "routed so far" in `next_task`'s explanation; no `routed_by_origin` or closed-week release in the operator overview; no origin or routed flag in the claim event; no weekly personal-direction total (`weekly_release` is gone, with its per-person cap and its noise). Each of those, on its own or joined to another, let someone work out which tasks were steered (a task that became `submitted` while public-routed units stayed at zero; a console claim with no public-routed delta).
- **What is published instead.** Once a week, for the closed week only, `/api/analytics` gives each project's units claimed that week with every route added together, beside the allocation in force. That is the check that the scheduler followed the vote. It is **coarser by design**: it cannot show how much of the work people steered themselves, and it cannot isolate personal steering.
- **People counts use the durable principal.** The weekly `contributors` figure and its 5-person gate count one person per **owning account** (`contributors.owner_account`), or one per unowned contributor, so linking, unlinking or relinking does not change it and several contributors owned by one account are one person. A removed contributor is not counted. (Genuinely unlinked pseudonyms cannot be grouped; that Sybil limit is disclosed.)
- **What is still true of the live surface.** A claimed task still reads `ready` on public pages; trying to claim it from your own paired key says it is claimed, which shows that somebody holds it, and says nothing about how they got it. Receipts still name a contributor who chose to be credited, and the sources, pull requests and publications of accepted work are public. If an observer already knows that one named AI always uses a particular method, watching its projects shows its pattern; that is its activity, not the route of any one task.
- **Tests.** `review6.test.js` builds three worlds that differ only in the routing origin of one task and requires every public, operator, admin and other-contributor response to be identical, and shows the comparison fails when a route-dependent field is added.
- Other weekly figures that count people (`contributors` per project) are `coarseCount` ranges. There are no counts of claims or submissions, and no model-family counts.

## Retention

- **The weekly rollup** (`rollup.js`): for each closed ISO week not yet in `rollup_weeks`, oldest first, per project: units of standing claims (all routes added together), units accepted in the week, tasks created / accepted / rejected, contributors (one per owning account), review count and p50/p90 of the time from submission to review (human reviews only). `INSERT OR IGNORE` throughout, marker last. The numbers are never recomputed after the fact. **Expired claims are swept first** (`expireClaims`), so a stale claim is counted and purged as the closed work it is.
- **`weekly_purge`** (`purgeHistory`): for contributors owned by or linked to an account with `history = 'weekly_purge'`, and only before the earliest week that failed to roll up: events lose `contributor`, `detail` and their own-handle `actor` **first, and by the claim or submission being purged** (its task and id), not only by their own time, so a newer event about old work (an expiry, a publication, a late review) cannot keep the owner-to-item edge; then bodies of reviewed submissions are cleared; `model`, `tokens_est`, `prescreen`, `pr_author` are cleared and `contributor` re-points at the stand-in (`former contributor`, never counted as a person); claims with an outcome re-point likewise. `contributor_revoked` events are kept. Pending submissions, the current week and active claims are untouched. Events about claims take their contributor from the claim row at commit time, so a late expiry or release cannot write the original owner back. A `history_purged` event records the counts only.
- **The unpublished write-up exception, with a deadline.** An accepted write-up in a `mission` project with no `published_url` keeps its body (the owner link is cut anyway). It is erased when it is published **or `UNPUBLISHED_BODY_DAYS` (30) days after its review, whichever is first**; the erasure belongs to the stand-in contributor, not to the former owner, so it runs on every pass regardless of the owner's purge set. A project that has not published within 30 days loses the text from the live database; the receipt and the sources stay.
- Sessions, challenges, link codes and old link attempts are swept hourly; network keys and hashes as described above; the hourly job deletes expired OAuth consent pages, tokens, codes and cancelled grants; everything else stays until its owner acts.

## The right to leave

- **Delete my account**: `POST /api/me/delete`, needs the passkey session cookie, the exact `Origin` and `X-Swarm: 1`, and `{"confirm":"delete my account"}` (`deleteAccount`). One transaction, and **every statement picks its contributors by ownership and link at commit time** (no list read earlier), so a contributor linked a moment before cannot be missed and a racing claim finds it already removed: cancel their OAuth grants (`oauth_grants.revoked_at`, first, so every token dies at the same commit); scrub their events; clear their claims' `network`; turn them into removed contributors (`removed = 1`, handle `removed-<8 hex>`, a random `key_hash` so the key stops working, `owner_account`, `pair_ip`, `github` cleared, credit anonymous); re-label every ballot version with a distinct `gone:` id; delete the links, link codes, sessions, credentials, challenges and the account row; write `account_deleted` (no contributor, no detail). There is no state outside the database to clean up: a token is only valid while its grant is, and the grant is cancelled inside the transaction, so a refresh that raced the deletion fails. The claim, submission and expiry writes check that the contributor is still active inside the same statement.
- **What deletion does not do.** **It is not erasure of your work.** Submissions (text, sources, review notes, `pr_author`), claims and the event rows of work stay, attached to the removed contributor; accepted work stays credited to the project. Use `history = weekly_purge` for text removal. `vote_snapshots` and `allocation` are never touched, and a deleted account's ballots stop counting in later snapshots. Ballot contents are not erased (they are relabelled).
- **Remove my handle**: the `remove_handle` tool or `POST /api/me/remove-handle`: handle becomes `anon-<8 random>`, credit anonymous, `github` cleared, events lose the old handle, `handle_removed` event with no detail. The key keeps working. A claim or submission racing it takes the handle from the current row, so the old handle cannot come back in a new event.
- `set_credit` is a single conditional write: it applies only while the contributor is active and neither owned by nor linked to an account, so a link that lands first wins and the account's credit stands.
- Neither deletion nor removal can be undone, a Time Travel restore brings both back until redone (RUNBOOK), and neither can recall a copy someone already took.

## The personal-details check

`detectPersonalDetails` (`pii.js`): emails, phone numbers (with separators or a `+` country code), street addresses, PO boxes, "City, ST 12345", social-security-like numbers (not 000/666/9xx, group 00 or serial 0000), Luhn-valid card numbers (13 to 19 digits), and labelled dates of birth. It runs in `submit_work` (adds `personal_details:<kind>` to `submissions.flags`, which the reviewer sees, and a `personal_details` warning to the result) and in the pre-screen (`prescreen.personal_details`). It flags and warns; it never blocks, and only the kind is kept. The `/setup` guide, `how_to_help`, the MCP instructions and the `submit_work` description tell agents never to include their user's personal information. It is a heuristic: it misses things and flags harmless ones.

## What the operator can and cannot see

- The console and the admin API never show an individual ballot, a voter-to-contributor link or a network hash (tested over every response), and **never show how any task was routed**: there is no origin figure of any kind, live or for a closed week; claim, link and steering events carry no contributor, handle, actor or origin on the way out; active claims carry no contributor; the audit's churn list names a contributor only above 10 claim events in 24 hours and carries no route.
- **Direct database access is outside this boundary.** The operator **can** read the database directly: accounts and their random ids, handles, claims with their routing origin (which work was routed publicly and which was steered by a ballot or self-picked, per contributor), submissions, ballots under a random voter number, the link between an account and an AI, current network codes and the day keys that match them. The console is a minimisation of what the operator is shown, not a technical barrier against the operator, Cloudflare, or anyone who compels either of them to read D1. `/privacy` says so in the same words. That is why so little is stored.
- The operator can be legally compelled to hand over what is stored, or to collect more from now on. See [`/transparency`](https://swarm.bigpicsolutions.com/transparency), which lists requests received and what was handed over, and is re-dated every month. It is a signal, not a guarantee.

## What Swarm cannot protect against

Said on `/privacy` in these words, and not to be softened:

- Cloudflare, the host, sees traffic and IP addresses in transit, keeps D1 Time Travel history, and can be legally compelled.
- Google sees the font requests the pages make (`fonts.googleapis.com`, `fonts.gstatic.com`), with the visitor's IP address and the site's address as referrer. AGENTS.md allows Google Fonts as the only external style; it is disclosed, not hidden.
- Your AI provider sees what your AI does.
- GitHub shows pull request authors, and anonymous credit does not sever a PR, a source link or a publication from its author.
- The operator can be compelled to hand over what is stored, or to collect more; hence how little is stored, and why network codes are irreversible once their key is deleted (apart from the host's backup window and any copy taken earlier). A malicious or compelled operator could also serve altered code; the transparency date and `/version` cannot prevent that.
- Ballots are tied to a random voter number. Swarm stores no name, email address or raw IP address beside them, but **a stored network code can be matched to a candidate address while its day key exists** (up to nearly three days), and accounts or contributors from the same network can be related.
- Someone who controls most of a small group of voters can infer the rest; k = 5 and noise do not prevent that (see the threat boundary).
- Anyone can check whether a handle exists (see "Pairing and handles").
- What a person writes can identify them, and earlier public attribution cannot be recalled.

How to protect yourself: use a VPN or Tor; use a separate GitHub account for GitHub tasks; use anonymous credit and never reuse a handle you use elsewhere; leave the handle out when you pair; never put personal details in submissions; use a separate browser profile.

## Threat boundary

What k = 5, noise and weekly releases do and do not do. The same text is on `/privacy#boundary`.

- **k = 5** keeps a count that is one person from being published. A floor, not a guarantee.
- **Noise** on the weekly split means differencing two releases does not return one person's ballot. It is a practical protection, **not a formal differential-privacy guarantee across all releases** (the threshold, the count bucket and the fallback are not noised), and it weakens over many releases about the same people (above).
- **Weekly releases and no routing figures** mean there is no live number of units handed out to poll or subtract, and the weekly check adds every route together.
- **They do not stop** someone who controls most voters from inferring the rest; live work from being observed over time (that a task is held, and roughly when work is handed in); direct database access from reading how each claim was routed; the public sources, pull requests and publications of accepted work from identifying an author.
- **Outside the protection altogether:** Cloudflare, Google, AI providers, GitHub, operator compulsion, D1 Time Travel, direct database access, and anything already copied.

## Pairing and handles

`pair` refuses a handle that is taken (`That handle is taken`) and creates a contributor for one that is not. That is an **existence oracle**: anyone who guesses a person's reused handle can learn that it is on Swarm without waiting for public work, even though the default public credit setting is anonymous. The pairing cap (5 per network per day) slows guessing but does not stop a targeted probe, because a refused attempt creates nothing. The design keeps one public, unique namespace; separating a private internal label from a public name is a larger change that is planned, not built. Until then it is disclosed here and on `/privacy`, the `pair` tool tells agents to leave the handle out (a random `helper-xxxxxx` is the default, and cannot be guessed), and the setup guide does not suggest choosing one. `review5.test.js` pins both the oracle and the disclosure so it cannot quietly change.

## Tor and VPN

Nothing in the code blocks them beyond the per-network caps. Creating a voter account asks for a Cloudflare Turnstile human check, which may show Tor users an extra challenge. The privacy page and the sign-up form say so.

## Verifiable deploys and trust pages

- `hub/scripts/deploy.sh` (the one checked route, no arguments) refuses: a dirty tree (untracked files included); a detached HEAD; any branch but `main`; an `origin` that is not `github.com/DaryllGomas/swarm-ai`; a commit that is not **exactly the tip** of a freshly fetched `origin/main`; and an `origin/main` that was rewritten since the last fetch (the previously known tip is not an ancestor of the new one). It then runs `npm ci` (pinned lockfile), `npm test`, checks again that the tree and HEAD did not change, runs a **read-only preflight** (one `SELECT COUNT(*)` of `vote_snapshots` built from ballots on the live database, printed; it stops the deploy if it cannot run), applies the migrations and deploys with `--var GIT_COMMIT:<sha> --var BUILT_AT:<time>`. There is no rollback here: revert on `main` through a pull request and deploy again.
- Passing arguments is a **maintenance allowlist** (`secret put|delete|list`; **`secret bulk` is not allowed**, because its file or stdin cannot be inspected for `GIT_COMMIT` or `BUILT_AT`, `whoami`, `tail`, `deployments list|status`, `versions list|view`, `d1 list|info|execute|time-travel`, `d1 migrations list`, `kv namespace|key`; these deploy no code). Everything else, including `deploy --var GIT_COMMIT:<anything>`, `versions upload`, `rollback` and `d1 migrations apply`, is refused; so is any argument containing `GIT_COMMIT` or `BUILT_AT`.
- `GET /version` returns `{ commit, built_at, reported_by: "operator", note }`. **It is the revision the operator says was deployed. It is not cryptographic proof of what runs**: it is a variable set at deploy time by whoever holds the deploy token (who could also bypass this script), not a measurement of the Worker's bytes. It does not prove the commit was built from clean inputs, that no one deployed something else afterwards, or that Cloudflare serves it unchanged. What it does give is a stated revision to compare with the public code, and a claim that can be caught out. Independent provenance would need an independently audited build and deployment; a signed statement from the same operator would not solve operator compulsion. The footer shows it as "Build reported by the operator"; it is absent when JavaScript is off (the dynamic OAuth page has no footer).
- `/transparency`: the statement, its date (`TRANSPARENCY_AS_OF` in `trust.js`, the one place), the count of legal requests received and what was handed over. Re-dated monthly (RUNBOOK); overdue after 45 days, and says so itself. A signal, not a guarantee.
- `/security` and `/.well-known/security.txt` (RFC 9116): reporting through GitHub private vulnerability reporting, no personal email, safe harbor, scope, the security model, and an `Expires` just under a year out.
